# QMonster Creator v0.1 Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the Task-10 preview into a release-verifiable v0.1 by fixing deterministic generation and validation defects, completing safe import/export, hardening local boundaries, and adding reproducible browser, performance, and visual gates.

**Architecture:** Preserve the existing npm-workspaces monorepo and its one-way package boundaries. Add deterministic rig selection and catalog-aware `MonsterSpec` validation in `generator-core`, make creator validity derive from generation plus current render diagnostics, keep failed IO diagnostics transient, and complete release evidence through Playwright and deterministic acceptance tooling.

**Tech Stack:** Node.js 22.16.0, npm 10.9.2 workspaces, TypeScript 7, React 19, Vite 8, Zod 4, Vitest 4, Playwright 1, fast-check 4, Canvas 2D, Sharp.

**Spec:** `docs/superpowers/specs/2026-08-23-qmonster-v0.1-hardening-design.md`

## Global Constraints

- Work only in the existing linked worktree on `feature/qmonster-v0.1`; preserve unrelated changes.
- Use TDD for every behavior change: observe a targeted failure, implement the minimum coherent fix, then run focused and integration tests.
- Public generation has exactly 14 visual slots, 8 semantic slots, themes `deep-sea`/`fungal`/`shadow`, and rigs `blob`/`biped`/`floating`.
- Rig choice uses `hash(seed, themeId, bodyFrame, rerollIndex, "rig")` and is uniform over rigs with a legal `bodyFrame` candidate.
- `colorScheme` is hard-bound to the active theme for random, locked, and manual-selection flows.
- `MonsterSpec` is renderable only when structure, catalog semantics, `schemaVersion`, `catalogVersion`, and `rendererVersion` are valid.
- Current-work validity is derived from generation and current render errors. Failed import/export and persistence diagnostics are transient display evidence and must not invalidate an otherwise valid current work.
- JSON import is transactional and limited to 1 MiB. Failed import never mutates the current session.
- Blocking current-work errors disable formal JSON, PNG, and WebP export. WebP capability failure alone leaves JSON and PNG available.
- `incubator-adapter` treats inputs as untrusted and returns explicit `AdapterResult<T>` values.
- Any stale-output deletion must remain inside canonical output roots even when symlinks or Windows junctions exist.
- Acceptance seeds are exactly `2026082101` through `2026082120`; themes cycle `deep-sea`, `fungal`, `shadow`; rigs arise naturally from the public generation path.
- Performance acceptance uses the current Windows machine: 100 warmed local rerolls with p95 <= 150ms and 10 PNG exports with every sample <= 2000ms.
- Do not update a reviewed golden merely to make a test pass. Review the rendered artifact and record the reason first.

- [ ] **Step 3: Implement the legal-rig substream**

Use this exact selection contract:

```ts
export function selectRigId(request: GenerationRequest, catalog: Catalog): RigId | null {
  const rerollIndex = request.slotRolls?.bodyFrame ?? 0
  const legal = catalog.rigs.filter(rig => catalog.parts.some(part =>
    part.slotId === 'bodyFrame'
    && part.compatibleRigs.includes(rig.id)
    && part.assetPath.trim().length > 0
    && part.baseWeight > 0,
  ))
  if (legal.length === 0) return null
  const rng = createRng([...slotSeedParts(
    request.seed, request.themeId, 'bodyFrame', rerollIndex,
  ), 'rig'])
  return pickWeighted(legal, () => 1, rng).id
}
```

`generateMonster` must use a legal locked-body rig when present, otherwise `selectRigId`; a null result produces `NO_COMPATIBLE_RIG`. `rerollSlot` must recompute the rig before resolving `bodyFrame`, then regenerate/revalidate descendants against the new rig.
