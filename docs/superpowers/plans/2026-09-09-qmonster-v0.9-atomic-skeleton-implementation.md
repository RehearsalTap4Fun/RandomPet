# QMonster v0.9 Atomic Skeleton Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship catalog/renderer/spec version `0.9.0/0.9.0/0.4.0` with one base feline skeleton, one legendary whole-skeleton variant, fixed-position full-context traits, sealed semantic allowlists, and no runtime structural assembly.

**Architecture:** Add a version-isolated v0.9 contract and generation path rather than widening the legacy v0.1-v0.8 types. Resolve a content-addressed release into an immutable `ResolvedV09Catalog`, generate a `MonsterSpecV09`, and render only its frozen 21-node composition graph with identity transforms. Produce both skeleton families and every trait projection in locked full-master workbenches, then activate the release only after validation, bulk visual approval, browser parity checks, and fixed-seed evidence succeed.

**Tech Stack:** Node.js `>=22.12.0`, TypeScript `~7.0.2`, Zod `~4.4.3`, Sharp `~0.35.3`, React `~19.2.8`, Vitest `~4.1.11`, Playwright `~1.62.1`, Canvas 2D.

**Spec:** `docs/superpowers/specs/2026-09-09-qmonster-v0.9-atomic-skeleton-authoring-design.md`

## Global Constraints

- Preserve v0.1-v0.8 files, schemas, catalogs, render routes, hashes, and reproducibility; never route an old spec through v0.9.
- Use exactly `{ schemaVersion: '0.4.0', catalogVersion: '0.9.0', rendererVersion: '0.9.0' }` for v0.9.
- Use 2048×2048 RGBA8 sRGB assets and binary masks whose RGB is zero and alpha is only 0 or 255.
- Select one base skeleton and one legendary whole-skeleton family with weights `8:1`; do not create a rare skeleton placeholder.
- Maintain exactly twelve v0.9 appearance slots, each with 8 common, 4 rare, and 1 legendary semantic traits for each skeleton family.
- Keep head, neck, torso, limbs, and the complete tail inside each skeleton master; never expose them as independently composited assets.
- Permit only `headAppendage` and `extraAppendage` to use `MasterAttachmentInterfaceV1`; the interface has no anchor, transform, crop, or runtime placement behavior.
- Reject fish tails, multiple heads, independent limbs, cross-species structural classes, unapproved hashes, and cross-skeleton projections before catalog activation.
- Traits cannot provide `zIndex`, transforms, crop rectangles, occluder masks, or arbitrary resource paths.
- Generate each user acceptance seed exactly once per release attempt; do not auto-review or resample visual results.
- Do not stage or modify the pre-existing dirty v0.6 connector work while implementing this plan.

- [ ] **Step 3: Implement RFC 8785-compatible JSON bytes and decoded pixel hashing**

Reject non-finite numbers before canonicalization. Decode PNG with Sharp to raw 2048×2048 RGBA, force sRGB, require one page, and hash `width || height || rawPixels` with SHA-256.

```ts
export async function decodedPngSha256(bytes: Buffer): Promise<string> {
  const image = sharp(bytes, { animated: false, failOn: 'error' }).toColourspace('srgb').ensureAlpha()
  const { data, info } = await image.raw().toBuffer({ resolveWithObject: true })
  if (info.width !== 2048 || info.height !== 2048 || info.channels !== 4) throw pngContractError()
  return createHash('sha256').update(`${info.width}x${info.height}:rgba8:`).update(data).digest('hex')
}
```
