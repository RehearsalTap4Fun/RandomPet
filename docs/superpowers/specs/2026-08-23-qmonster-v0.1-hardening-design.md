# QMonster Creator v0.1 收尾与发布加固设计

- 日期：2026-08-23
- 状态：已完成对话设计评审，待书面规格复核
- 基线分支：`feature/qmonster-v0.1`
- 前置规格：`docs/superpowers/specs/2026-08-21-qmonster-creator-design.md`
- 前置计划：`docs/superpowers/plans/2026-08-21-qmonster-creator-implementation.md`

## 1. 背景与目标

当前分支已经完成实施计划 Task 1–10 的主要代码和素材交付，但审核确认它仍是 Task 10 后的功能预览版：Task 11、Task 12 尚未实现，同时生成、诊断、渲染和本地生产脚本存在发布阻断问题。

本设计定义 v0.1 收尾阶段的唯一实施口径，目标是：

1. 修复三骨架生成、主题锁定、局部诊断和渲染边界的正确性问题。
2. 完成安全、事务式的 JSON 导入及 JSON/PNG/WebP 导出。
3. 加固孵化器适配器、本地素材清理脚本和浏览器持久化边界。
4. 完成 Task 12 的行为、性能、跨浏览器和视觉发布门禁。
5. 产生可复核的 v0.1 发布报告，而不是仅依赖“测试文件存在”。

## 2. 范围

### 2.1 包含

- 审核报告中的全部阻塞问题。
- Coverage 稳定性、适配器覆盖、本地持久化资源上限和性能环境定义等建议项。
- Task 11、Task 12 和 Final Verification。
- 对原设计规格和实施计划的必要澄清。

### 2.2 不包含

- 后端、账号、云同步或多人协作。
- 修改外部孵化器仓库。
- 增加第四种主题、第四种骨架或新的正式内容预算。
- 重写现有 Monorepo 或替换 Canvas 2D 渲染方案。

## 3. 总体实施策略

保持现有包边界，按五个串行门禁推进：

1. 生成核心与会话正确性。
2. 渲染、版本、适配器及文件系统安全边界。
3. Task 11 事务式导入导出。
4. Task 12 自动化与视觉验收。
5. 全量发布验证和分支复核。

每个门禁均先补充可稳定复现的失败测试，再做最小实现，随后运行任务级测试和独立代码复核。后续门禁不得建立在尚未通过复核的前置门禁上。

## 4. 确定性骨架与 `bodyFrame`

### 4.1 骨架子流

骨架选择使用独立子流：

```text
hash(seed, themeId, bodyFrame, rerollIndex, "rig")
```

从当前目录中具有合法 `bodyFrame` 候选的骨架集合中等权选择。候选骨架按目录中声明的稳定顺序参与抽取；没有合法 `bodyFrame` 的骨架不得进入集合。

选择骨架后，再使用现有 `bodyFrame` 槽位子流在该骨架兼容的部件中完成主题、稀有度和权重抽取。骨架子流与部件子流分离，避免给骨架选择增加随机消费后破坏部件抽取的可解释性。

### 4.2 锁定与重抽

- 锁定 `bodyFrame` 时，由锁定部件确定骨架。
- 局部重抽 `bodyFrame` 时递增其 `rerollIndex`，允许确定性切换骨架。
- 骨架变化后重算全部未锁定下游槽位。
- 已锁定但与新骨架不兼容的下游槽位保留原选择，并产生阻断诊断。
- 正常生成和 `bodyFrame` 重抽必须通过固定 seed 集合证明能够覆盖 `blob`、`biped`、`floating`。

## 5. 主题绑定与局部诊断生命周期

`colorScheme` 是主题硬绑定槽位。随机、锁定和手动选择三条路径都必须验证 `part.themeIds` 包含当前主题。

主题切换遇到不兼容的锁定配色时：

1. 保留用户锁定的原选择。
2. 返回指向 `visualSlots.colorScheme` 的 `LOCK_INCOMPATIBLE`。
3. 将会话标记为 `blocked`。
4. 不得静默替换配色。

局部生成结果增加“实际受影响槽位集合”。reducer 只替换该集合内可替换的旧槽位诊断，同时保留未受影响槽位、全局目录错误和未知错误。父槽位重抽修复下游问题后，下游旧错误必须消失，`blocked` 必须重新按当前诊断计算。

## 6. 统一的 `MonsterSpec` 目录与版本校验

新增公共校验边界 `validateMonsterSpecAgainstCatalog`，至少检查：

- `schemaVersion` 是否受当前应用支持。
- `catalogVersion` 是否与实际加载目录精确一致。
- `rendererVersion` 是否受当前渲染器支持。
- 14 个槽位的 `partId` 是否存在且属于正确槽位。
- `selection.rigId` 是否存在且属于部件的 `compatibleRigs`。
- 必需 socket、互斥关系、主题绑定和批准的 transform 是否成立。
- modifier 是否存在、类型匹配且 overrides 与目录一致。

该校验用于四个入口：文件导入、预览渲染、正式图片导出和孵化器记录输出。Schema 结构合法不再等同于目录语义合法。

函数返回 `Diagnostic[]`；空数组表示校验通过，任一 `severity=error` 表示阻断。调用方不得把 warning 自动升级为 error。

## 7. 统一诊断与导出阻断

`CreatorSession` 成为生成和渲染诊断的唯一状态源。会话以 `generationDiagnostics` 和 `renderDiagnostics` 分别保存两类诊断，由纯函数 `mergeSessionDiagnostics` 向 UI 提供去重结果；`blocked` 始终等于合并结果中是否存在 `severity=error`。现有单一 `diagnostics` 字段迁移为该派生结果，不再作为第三份可独立修改的状态。

`PreviewCanvas` 的非陈旧渲染结果通过 reducer action 回写渲染诊断。陈旧异步请求不得覆盖新请求的画面或诊断。正式导出必须读取统一的 `blocked`，不能只依赖生成阶段结果。

以下能力规则固定：

- 存在任一阻断错误：禁用正式 JSON、PNG、WebP。
- 无阻断错误且 PNG 可用：允许 JSON 和 PNG。
- WebP 不支持：仅禁用 WebP，并显示明确 warning；JSON 和 PNG 保持可用。
- 所有图片编码器不可用：JSON 仍可用。

## 8. Task 11：事务式导入导出

### 8.1 JSON 导入

导入流程为两阶段事务：

1. 拒绝大于 1 MiB 的文件，把内容解析为 `unknown`，调用 `parseMonsterSpec`。
2. 使用注入的 `CatalogRegistry` 按精确 `catalogVersion` 加载目录，再执行 `validateMonsterSpecAgainstCatalog`。

只有两阶段全部成功后，才派发 `importSpec`。任何失败都不得部分更新当前会话。导入成功后清空全部编辑锁，并按导入结果重新渲染和计算诊断。

### 8.2 文件导出

- JSON 文件名：`qmonster-{themeId}-{seed}.json`。
- PNG 文件名：`qmonster-{themeId}-{seed}.png`。
- WebP 文件名：`qmonster-{themeId}-{seed}.webp`。
- JSON 使用两空格缩进并以换行结尾。
- 图片下载复用 `exportCanvas`，验证 MIME，触发下载后释放 object URL。
- `WEBP_EXPORT_UNSUPPORTED` 转换为可见 warning，不得吞掉或升级为全局阻断。

## 9. 集成与本地安全边界

### 9.1 `incubator-adapter`

孵化器输入视为不可信边界。新增严格运行时 Schema，并把 `toGenerationRequest`、`toIncubatorRecord` 改为显式 `Result<T>`：

```ts
type AdapterResult<T> =
  | { ok: true; value: T }
  | { ok: false; diagnostics: Diagnostic[] }
```

- 主题只能是 `deep_sea`、`fungal`、`shadow`。
- seed 只能是字符串或有限数值，标准化后的字符串长度不得超过 128。
- `risk`、`mutationBonus` 必须是有限数值，再按业务范围归一化。
- 输出前必须完成 `MonsterSpec` 结构、目录语义和版本校验。
- 失败返回结构化诊断，不抛出不可判定的边界异常，也不产生部分记录。

### 9.2 `safe-output`

删除任何文件前：

1. 对输出根和目标目录解析 canonical `realpath`。
2. 验证 canonical 目标仍位于 canonical 根内。
3. 拒绝作为清理目录的符号链接或 Windows junction。
4. 对每个待删除文件再次验证 canonical 父目录。

测试必须创建指向根外临时目录的真实链接，并证明根外图片不被删除。

### 9.3 本地持久化

保存和读取采用同一组上限：

- 序列化 UTF-8 大小不超过 1 MiB。
- diagnostics 不超过 256 项。
- 单个 diagnostic path 不超过 16 段。
- code 不超过 128 个 Unicode code point。
- 单个 path segment 不超过 256 个 Unicode code point。
- message 不超过 2048 个 Unicode code point。

超限数据按 `SESSION_LOAD_FAILED` 或 `SESSION_SAVE_FAILED` 降级，不进入部分会话。

## 10. Task 12：自动化发布门禁

### 10.1 浏览器与像素测试

- 已审 RGBA golden 只在计划指定的 bundled Chromium 项目比较。
- Chrome Stable、Edge Stable、Firefox、WebKit 分别验证同一引擎内同一 `MonsterSpec` 的重复渲染像素一致。
- 不要求不同浏览器之间生成完全相同的 Canvas RGBA，因为浏览器栅格器可能存在实现差异。
- 每次 viewport 改变并 reload 后，布局测试必须重新等待应用 ready，再读取 DOM。

### 10.2 用户工作流

真实浏览器 E2E 至少覆盖：

- 整只生成、锁定、局部重抽和手动选择。
- 主题切换后的兼容锁保留与不兼容锁阻断。
- 合法 JSON 导出再导入后的配方和同引擎像素一致。
- 无效导入不改变当前作品。
- 阻断诊断禁止正式导出。
- WebP 不支持时 JSON/PNG 保持可用。

### 10.3 Coverage 稳定性

生产图像和目录校验测试与轻量单元测试分组。重型测试使用根据干净基线实测确定并写明理由的专用超时，不通过简单扩大所有测试的全局超时掩盖性能退化。Coverage 命令必须在干净工作树中连续两次退出 0。

## 11. 性能基准

v0.1 使用执行发布验收的当前 Windows 机器作为基准机。发布报告必须记录：

- CPU 型号、逻辑核心数和内存容量。
- Windows 版本与电源模式。
- Node.js、npm、Chromium、Chrome Stable 和 Edge Stable 的精确版本。
- Git commit、`schemaVersion`、`catalogVersion`、`rendererVersion`。

性能流程固定为：

1. 预热当前主题和当前作品引用的素材。
2. 通过产品公开命令连续执行 100 次局部重抽，统计从 command start 到非陈旧 preview commit 的 p95，要求不超过 150ms。
3. 连续执行 10 次 1024×1024 PNG 导出，每次要求不超过 2 秒。
4. 记录每个样本和汇总值；失败样本不得从统计中删除。
5. 连续重抽期间验证 Canvas 和图片缓存没有单调无界增长。

## 12. 20 只视觉验收口径

验收 seed 固定为 `2026082101` 至 `2026082120`，按顺序执行。主题按 `deep-sea → fungal → shadow` 循环预设；每只都必须通过产品公开的整只生成命令产生。

骨架由正常确定性骨架子流自然抽取，不允许直接注入、覆盖或事后替换。如果 20 只结果没有覆盖 `blob`、`biped`、`floating`，验收直接失败并修正规则或重新提交产品决策，不能选择性丢弃样本。

每次执行保存：

- 顺序、seed、themeId、实际 rigId。
- 完整 `MonsterSpec`。
- 透明 PNG。
- 机器可读 `acceptance-set.json`。
- 编号 contact sheet。

逐只检查肢体连续、落地、遮挡、穿插、镜头、光照、五官透视、材质、配色、友善怪奇感和主题可辨识度。任何失败都要求修复后重新开始 20 只连续验收。自动生成与初步视觉检查完成后，最终 contact sheet 交由用户确认。

## 13. 发布完成定义

只有同时满足以下条件，才允许声明 v0.1 发布就绪：

1. 类型检查、全部 Vitest、Coverage、目录校验和生产构建退出 0。
2. 五个 Playwright 项目的适用工作流全部通过。
3. 已审 Chromium golden 不变，或其变化已完成人工复核并记录原因。
4. JSON 往返、目录版本、渲染版本、阻断导出和能力降级测试通过。
5. 性能和缓存增长门禁通过。
6. 固定 20 只验收集覆盖三主题与三骨架，并连续通过视觉检查。
7. `incubator-adapter` 在三主题、三骨架和所有模式下输出合法的 8 个主特征。
8. `docs/qa/v0.1-release-report.md` 记录全部环境、测试、性能、种子和视觉证据。
9. 工作树不存在未追踪的发布生成物，完整分支复核没有未处理的阻塞问题。

## 14. 迁移与兼容说明

`incubator-adapter` 的转换函数从直接返回值改为 `Result<T>` 是有意的破坏性 API 调整。本仓库内调用点和测试必须同步迁移。外部孵化器仓库不在本次修改范围内，因此发布报告必须明确记录该接口变化及调用方迁移示例。

现有合法 `MonsterSpec` 数据格式不因本设计新增字段；新增的是更严格的版本和目录语义校验。无法满足当前版本策略的旧数据必须返回结构化诊断，不得静默升级或回退。
